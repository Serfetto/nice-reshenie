# Архитектура: сервис поддержки планирования ВКД на МКС

КосмоХакатон 2026, кейс «Прогнозирование внешних рисков и планирование ВКД на МКС».
Статус: проектный документ от 2026-09-19 (изменения относительно первой версии основаны на QA-сессии 18.09, §21).
Он описывает замысел шире реализованного. Что работает в сдаваемой версии (алгоритм 0.0.1), — в
[README](../README.md), [method.md](method.md) и [sources.md](sources.md).

**Реализовано иначе или не реализовано:**

| В документе | В коде |
|---|---|
| Интерфейс React + TypeScript, Telegram на aiogram, `skyfield` | обычный HTML/CSS/JS + Plotly, Telegram — прямой вызов Bot API (httpx), только `sgp4` |
| Орбита по NASA OEM, сверка с OEM | только TLE Space-Track (история `gp_history` с `CREATION_DATE`), резерв — CelesTrak |
| Сближения SOCRATES | не используется (нет архива) — собственный отбор по каталогу Space-Track |
| DONKI, рентген и вспышки как предвестник протонов | не реализовано (развитие) |
| Метеорные потоки NASA MEO | реализовано как статистическая часть MMOD (method.md, §4) |
| Этапы ВКД (`phases`), сценарии «продолжать / сократить / перенести» | не реализовано; есть запас на задержку и сравнение со временем возвращения в шлюз в оповещениях |
| Таблицы `ephemerides`, `conjunctions` | нет: элементы — в `elements`, сближения считаются при каждом расчёте |

## 1. Назначение

Исследовательский прототип для аналитика наземной группы планирования выходов в открытый космос (ВКД). Аналитик задаёт длительность выхода и период, в который его можно начать. Система:

- рассчитывает положение МКС на весь интервал;
- оценивает не менее двух разных механизмов внешнего воздействия;
- делит факторы на критические и нежелательные;
- сравнивает окна одинаковой длительности и формулирует рекомендацию;
- отслеживает утверждённый план и оповещает, если обстановка ухудшилась;
- показывает, на каких наблюдениях и прогнозах основан каждый вывод и насколько он надёжен.

**Пользователи:**

- **основной** — аналитик группы планирования ВКД (ГОГУ);
- **дополнительные**, как доп. функции: руководитель, которому передаётся рекомендация (краткая сводка), и экипаж (строка статуса, §10.3).

**Система не делает:**

- не выдаёт разрешение на выход и не заявляет «безопасно»: решение остаётся за уполномоченными специалистами;
- не рассчитывает дозу космонавта, вероятность повреждения скафандра или вероятность попадания фрагмента в человека. Мы оцениваем внешние условия и их последствия для окна работ качественно, с явными границами интерпретации;
- не использует ML в базовой версии. Постановка и эксперты: усложнение оправдано только доказанной пользой (§21).

## 2. Пользователи и сценарии

### 2.1. Запрос

| Параметр | Значения |
|---|---|
| Режим | «Сейчас» / «История: разбор» / «История: прогноз из прошлого» (replay) |
| Момент T | Для истории: дата и время в пределах 2024-05-01 … 2024-06-30. Для replay — момент отсечения |
| Длительность выхода | 1–8 ч |
| Период поиска начала | самое раннее и самое позднее начало. **До 24 ч гарантированно** (проверочный диапазон постановки), **до 72 ч** — с явно пониженной уверенностью |
| Плановое начало | опционально: окно, с которым сравниваются остальные |
| Параметры ВКД | время возвращения в шлюз, запас на задержку, опционально этапы выхода (§9.8) |
| Переопределения источников | заморозить на момент X / отключить; действует только на этот расчёт |

### 2.2. Ответ

- Временная шкала по каждому механизму в трёх слоях: измерение → условие на траектории → последствие для ВКД (§5).
- Трасса МКС с отмеченными участками: Южно-Атлантическая аномалия (ЮАА), открытые для солнечных частиц зоны, проходы через зону контроля сближений, тень.
- Таблица окон: по каждому механизму минуты по классам (критический / нежелательный / приемлемый / нет данных), уверенность, устойчивость к задержке.
- Итоговый статус окна: **предпочтительно / равнозначно / не рекомендуется (критический фактор) / требует проверки / недостаточно оснований**. К статусу прилагаются сработавшее правило, компромиссы между механизмами и ограничения.
- «Когда пересчитать»: время ближайших выпусков прогнозов, которые уточнят оценку.
- Ссылки на доказательства: значение → время → исходная запись.

### 2.3. Путь аналитика

1. Задаёт запрос и нажимает «Рассчитать». Видит прогресс: данные → орбита → факторы → окна.
2. Смотрит шкалу, трассу и таблицу окон.
3. Раскрывает предупреждение: смысл для ВКД, класс, значения с единицами, время выпуска, источник, правило, уверенность.
4. Двигает начало и отдельно длительность. Сокращение выхода помечается как изменение плана, а не как улучшение.
5. Сохраняет результат: HTML-отчёт, краткую сводку, ZIP-архив.
6. Ставит выбранное окно **на отслеживание** (§2.4).
7. Только в replay: нажимает «Что было на самом деле» и видит сверку прогноза с фактом.

### 2.4. Отслеживание плана

1. Аналитик ставит на отслеживание утверждённое окно или идущий выход.
2. При каждом поступлении данных по связанным источникам и по таймеру окно пересчитывается тем же ядром.
3. Если класс ухудшился, появился критический фактор (например, сближение в окне) или пропали данные по критическому фактору, приходит **оповещение**: в консоли, в Telegram, в строке статуса.
4. Для идущего выхода в оповещении указан запас времени относительно времени возвращения в шлюз.
5. Аналитик подтверждает получение. Повторные оповещения по тому же эпизоду не дублируются, приходят только эскалации.

## 3. Режимы работы

| Режим | Отсечка T | Какие данные доступны расчёту |
|---|---|---|
| Сейчас | текущий момент | всё полученное, с автообновлением |
| Сейчас: отслеживание | текущий момент, сдвигается | то же, пересчёт по событиям и таймеру |
| История: разбор | конец выбранного интервала | весь архив, включая поздние уточнения; результат помечается «реконструкция» |
| История: прогноз из прошлого | момент T | только записи с `issued_at ≤ T`, включая орбиту, созданную до T |

Код расчёта для всех режимов **один**. Режимы различаются только срезом данных `as_of(T)`.

**Автономная работа.** Без доступа к внешним источникам все режимы работают на локальном кеше. Давность данных видна, недостающие интервалы получают «нет данных» (§13).

## 4. Принципы

1. **Сырые данные неизменяемы.** Всё остальное выводится из них. Любое число прослеживается до исходного файла, любой расчёт можно повторить.
2. **Ядро не знает текущего времени.** Оно получает только срез `as_of(T)`, поэтому подсмотреть будущее в replay физически невозможно.
3. **У каждого значения есть происхождение:** тип (наблюдение / внешний прогноз / расчёт команды), источник, время выпуска, ссылка на сырьё.
4. **«Нет данных» — полноценное состояние.** Оно никогда не превращается в «норму».
5. **Критические факторы ничем не компенсируются.** Механизмы не складываются в одно число. Хорошие данные по одному механизму не перекрывают отсутствие данных по критическому фактору другого. Связанные сигналы (CME → буря → G-предупреждение; вспышка → протонное событие) не учитываются несколько раз.
6. **Расчёт — неизменяемый объект:** запрос, отсечка, версии, использованные сырые файлы, результат. Расчёты и подписки разных пользователей не смешиваются.
7. **Автономность.** В пути расчёта нет облачных сервисов. Внешняя сеть нужна только сборщику данных.

## 5. Факторы и классификация рисков

Разделение на критические и нежелательные факторы повторяет реальную практику. Критические показатели требуют возвращения экипажа. Нежелательные не позволяют планировать выход на определённый интервал (§21, п. 1). Таблица ниже — основа правила выбора окна (§9.7). Полное обоснование хранится в `docs/method.md`, пороги — в `config/thresholds.yaml`.

### 5.1. Три слоя интерпретации

| Слой | Что это | Пример |
|---|---|---|
| Измерение | внешняя величина, где и кем измерена | поток протонов ≥100 МэВ на GOES-18 (геостационар), наблюдение |
| Условие на траектории | что это значит в точке, где находится МКС | 06:12–06:24 МКС в открытой зоне: Rc ниже жёсткости протонов ≥100 МэВ |
| Последствие для ВКД | класс с учётом длительности и этапов работ | критический: выход в этот интервал не рекомендуется; при идущем выходе — сигнал на возвращение с запасом ≥ времени возвращения в шлюз |

### 5.2. Классы

| Класс | Смысл | Влияние на окно |
|---|---|---|
| `critical` | стоп-фактор: при таких условиях выход не планируют, а идущий прерывают | окно «не рекомендуется» |
| `undesirable` | нежелательно, но не критично | понижает окно в ранжировании |
| `acceptable` | фон, ожидаемые условия | — |
| `no_data` | нет наблюдения или действующего прогноза, либо источник устарел | по критическому фактору → окно «требует проверки» |

### 5.3. Факторы (пороги — черновые, подлежат обоснованию)

| Механизм | Фактор | `critical` | `undesirable` | Роль |
|---|---|---|---|---|
| Радиация | Солнечное протонное событие × геометрия | поток выше порога **и** МКС проходит открытую зону в окне | поток повышен, но МКС под защитой магнитного поля | основной фактор |
| Радиация | Проходы ЮАА | — | минуты в ЮАА (ожидаемый фон, минимизируем) | различает окна в спокойные дни |
| Радиация | Геомагнитная буря (Kp) | — | — | **не отдельный риск**: модификатор Rc, расширяет открытую зону |
| Радиация | Солнечная вспышка (рентген) | — | — | **не отдельный риск**: предвестник протонного события, вход прогноза (§9.4) |
| MMOD | Сближение с отслеживаемым объектом | время наибольшего сближения в окне (плюс запас) и проход через зону контроля | сближение рядом с окном, в пределах запаса на задержку | **стоп-фактор по бинарному принципу**: вероятность попадания не оценивается |
| MMOD | Метеорный поток | — | коэффициент к фону выше порога и радиант не закрыт Землёй | второстепенный |

### 5.4. Что сознательно не включено

| Кандидат | Почему не фактор |
|---|---|
| Радионарушения (шкала R) | другое явление: влияют на КВ-радиосвязь, а не на условия ВКД. Вспышка используется только как предвестник протонов |
| Освещённость (свет/тень) | условие работ, а не опасность. Может задаваться как ограничение пользователя, не как риск |
| DONKI GST, Kp с разных сайтов | повторы одного измерения, а не независимое подтверждение |
| Электроны на геостационаре (>2 МэВ) | относятся к зарядке спутников на геостационаре; связь с ВКД на МКС требует отдельного обоснования — отложено |
| Солнечный ветер (ACE/DSCOVR) | даёт 30–60 мин до прихода бури; полезно для оценки Kp «на сейчас» — развитие, не базовая версия |

## 6. Общая схема

```
             ┌───────────────────────────────────────────────────────────┐
 Аналитик ─► │ report: консоль · краткая сводка · строка статуса ·       │ ─► Telegram
 Руковод.  ─►│         экспорт · доставка оповещений (SSE)               │
             └───────┬──────────────────────────────┬────────────────────┘
                     │ /runs /watches /alerts       │ /sources
                     ▼                              ▼
┌──────────────────────────────────────┐  ┌────────────────────────────────────┐
│ assessment (оценка окон)             │  │ ingest (сбор данных)               │
│  задания расчёта + прогресс          │  │  планировщик по источникам         │
│  срез as_of(T, overrides)            │  │  адаптеры: fetch() + parse()       │
│  ядро: орбита → механизмы → классы → │  │  статусы и свежесть источников     │
│        окна → объяснения             │  │  загрузка архивов (backfill)       │
│  предрасчёт орбиты и сближений       │  │  NOTIFY «новые данные»             │
│  watch: отслеживание и оповещения    │  │                                    │
│  сверка replay (verify)              │  │                                    │
└───────────────┬──────────────────────┘  └──────────────┬─────────────────────┘
                │ читает данные, пишет runs/alerts       │ пишет сырьё и записи
                ▼                                        ▼
        ┌─────────────────────────────────────────────────────────────┐
        │ PostgreSQL (записи, эпизоды, эфемериды, runs, watches,      │
        │ alerts) + LISTEN/NOTIFY + том data/raw (только добавление)  │
        └─────────────────────────────────────────────────────────────┘
                                   ▲
 NOAA SWPC · NCEI · NASA DONKI · NASA OEM · CelesTrak · Space-Track · GFZ · NASA MEO
```

- `ingest` и `assessment` не вызывают друг друга за данными. Общий слой — БД. Сигнал «пришли новые данные по источнику X» передаётся через `NOTIFY` PostgreSQL, без брокера сообщений.
- Падение сборщика не роняет расчёт: `assessment` увидит устаревшие данные, отметит это и отправит оповещение о потере данных по отслеживаемым планам.
- `report` не считает. Он отвечает за все каналы для пользователя: веб-интерфейс, Telegram, экспорт.
- PostgreSQL: в БД одновременно пишут несколько процессов в разных контейнерах.
- Для хакатона: один репозиторий, общий пакет `common` со схемами, запуск через `docker-compose`.

## 7. Сервис `ingest` — сбор данных

### 7.1. Адаптер источника

Один модуль на источник, у каждого одинаковый контракт:

- `fetch(params) -> RawFile`: скачивает и сохраняет файл как есть, пишет журнал;
- `parse(raw_file) -> list[Record | Message | Ephemeris | ...]`: разбирает сырьё в единые записи.

После успешного разбора новых записей — `NOTIFY new_data, '<source>'`.

### 7.2. Расписание

Задаётся в `config/sources.yaml` под ритм публикации источника. Аналитик расписание не меняет, он видит его на панели источников (§12).

| Источник | Публикация | Опрос | Допустимая давность* |
|---|---|---|---|
| Протоны GOES, SWPC JSON | каждые 5 мин | 5 мин | 15–30 мин |
| Рентген GOES и список вспышек, SWPC JSON | 1 мин / по событию | 1–5 мин | 15 мин |
| Алерты и предупреждения SWPC | по событию | 1–5 мин | 30 мин |
| Kp наблюдённый и прогноз, SWPC JSON | 3-часовые значения | 15–30 мин | 3–4 ч |
| 3-дневный прогноз SWPC | 00:30 и 12:30 UTC | после выпуска + раз в час | 12–13 ч |
| RSGA (вероятности протонных событий) | 22:00 UTC | после выпуска | 24–26 ч |
| DONKI (api.nasa.gov) | по событию | 30–60 мин | 2 ч |
| TLE МКС, CelesTrak | несколько раз в сутки | раз в 2 ч (чаще CelesTrak блокирует) | 1–2 сут |
| Эфемериды NASA OEM | новый файл раз в 2–5 дней | раз в сутки | до конца охвата файла |
| Каталог GP для отбора сближений (CelesTrak, Space-Track) | несколько раз в сутки | раз в 8 ч | 1 сут |
| Сближения SOCRATES | 1–2 раза в сутки | 2 раза в сутки | 1 сут |
| Прогноз метеорных потоков NASA MEO | раз в год | раз в сутки проверка | 1 год |
| Архивы: GFZ Kp, GOES L2 (NCEI), NCEI SWPC products | с задержкой в дни | раз в сутки | — |

\* Черновые значения, уточняются в `sources.yaml`. Старше допустимой давности → статус `stale`, и в расчёте интервалы этого источника становятся «нет данных» (§13).

При ошибках интервал повторных попыток растёт. Запросы условные (`If-Modified-Since`, `ETag`), где сервер их поддерживает.

### 7.3. Сырые файлы и журнал загрузок

- Файл сохраняется в `data/raw/<source>/<yyyy>/<mm>/<dd>/<fetched_at>_<sha256[:12]>.<ext>` **только если хеш изменился**. Иначе журнал отмечает «без изменений».
- Журнал `raw_files`: source, url, fetched_at, http_status, sha256, size, content_type, parser_version, результат разбора.
- Сырые файлы не удаляются и не перезаписываются. Политика хранения — в §7.6.

### 7.4. Разбор: единая запись

| Поле | Смысл |
|---|---|
| `source`, `product` | например `swpc`, `goes_integral_protons` |
| `quantity`, `unit` | `proton_flux_ge10MeV`, `pfu`; `kp`, `—`; `xray_flux_long`, `W/m²` |
| `value` / `level` | число или уровень шкалы (S1, G3, M5.2, …) |
| `valid_from`, `valid_to` | к какому интервалу относится значение |
| `issued_at` | **время публикации из самого документа** (`Issue Time`, `:Issued:`, `CREATION_DATE`, `submissionTime`) |
| `fetched_at` | когда мы получили |
| `kind` | `observation` / `forecast` / `message` / `derived` |
| `region` | `geo` (геостационар) / `planetary` / `iss_orbit` / `sun` |
| `quality` | флаги: качество GOES, смена спутника, `preliminary`/`definitive` у Kp, «создано позже события» |
| `issued_at_policy` | `exact` / `reconstructed` (время выпуска неизвестно) |
| `raw_ref` | id сырого файла + локатор (строка, индекс, серийный номер) |

Правила разбора:

- **Алерты SWPC** разбираются в структуру: код, серийный номер, `Issue Time`, начало / максимум / конец, `Valid From/To`. Цепочки «предупреждение → продление (`Extension to Serial Number`) → алерт → сводка» склеиваются в **эпизод**. В расчёте эпизод — одно событие, а не три.
- **Дубли**: одно сообщение из `alerts.json` и из архива = одна запись. Перепечатка одного измерения на двух сайтах не считается независимым подтверждением.
- **Разная частота**: приводим к общей сетке при расчёте, а не при хранении. Через пропуски **не интерполируем**.
- **Версии DONKI**: записи переписываются задним числом (`versionId`, `submissionTime`). Храним все версии, срез берёт последнюю до T.

### 7.5. Статусы источников

`ok` · `stale` (старше допустимой давности) · `error` (последняя попытка упала: HTTP, квота, разбор) · `disabled` · `frozen`. Для каждого источника хранятся: последнее успешное получение, последняя ошибка, число неудачных попыток подряд, ожидаемое время следующей публикации. Смена статуса тоже отправляет `NOTIFY`: она нужна отслеживанию (§9.10).

### 7.6. Загрузка архивов и хранение

- `backfill` — разовая загрузка архива за период: исторический период кейса (май–июнь 2024) и контрольные периоды для экспериментов. Запускается командой CLI.
- Хранение сырья: подробно — не меньше исторического периода и последнего месяца оперативных данных. Дальше хранятся только изменившиеся файлы. Сроки задаются в конфиге.
- Архив и БД можно выгрузить одним пакетом для работы на изолированной машине (§13).

## 9. Сервис `assessment` — оценка окон

### 9.1. Задание расчёта

`POST /runs` создаёт задание со статусом `queued`. Этапы с прогрессом:
`slice` → `orbit` → `mechanisms` → `classify` → `windows` → `explain` → `done` / `failed`.

Результат сохраняется в `runs` целиком и больше не меняется. Повторный расчёт создаёт новый `run`. Целевое время расчёта — §14.

### 9.2. Срез `as_of(T, mode, overrides)`

- Записи с `issued_at ≤ T`; для версионных источников — последняя версия до T.
- Орбитальные элементы: среди наборов с `CREATION_DATE ≤ T` берётся набор с самой поздней эпохой. Порядок публикации не совпадает с порядком эпох, а один набор бывает переиздан с той же эпохой. У МКС на 2024-05-10 было 7 наборов, из них два с одинаковой эпохой.
- `overrides`: `frozen@X` — источник виден как на момент X; `disabled` — источник отсутствует.
- Режим «разбор» дополнительно открывает поздние уточнения (окончательный Kp GFZ, итоговые сводки SWPC) и ставит пометку «реконструкция».
- На выходе, кроме данных, — манифест: какие сырые файлы и версии вошли, что отброшено как опубликованное после T.

### 9.3. Орбита

- «Сейчас»: TLE → SGP4. Текущий OEM используется для сверки и оценки неопределённости орбиты. **Трек на 72 ч вперёд с атрибутами предрасчитывается** при каждом обновлении эфемерид (`orbit_cache`); запрос его только читает.
- История: OEM с `CREATION_DATE ≤ T` (прогнозная эфемерида на 15 суток, шаг 4 мин, система EME2000). Опционально история TLE из Space-Track (`GP_HISTORY` с `CREATION_DATE`). Современная орбита не подменяет историческую.
- Сетка 30 с на интервале [раннее начало; позднее начало + длительность + запас на задержку].
- Переводы систем: EME2000/TEME → ITRF → геодезические координаты.
- Атрибуты каждой точки:
  - широта, долгота, высота;
  - параметр магнитной оболочки L и модуль поля |B| по модели IGRF;
  - жёсткость геомагнитного обрезания Rc (приближение Штёрмера `Rc ≈ 14.9 / L²` ГВ) с поправкой на Kp;
  - флаг ЮАА (|B| на высоте МКС ниже порога);
  - свет / тень;
  - видимость радианта метеорного потока (не закрыт ли Землёй).
- Показываются источник, эпоха и давность орбитальных данных.

### 9.4. Механизм 1 — радиационная обстановка на траектории (космическая погода)

**Обстановка снаружи E(t):** поток протонов ≥10 и ≥100 МэВ, Kp.

- До T — наблюдение (GOES, Kp).
- После T, по приоритету:
  1. действующее предупреждение или эпизод SWPC — внешний прогноз;
  2. собственный прогноз на 6 ч — расчёт команды:
     - во время события: сохранение текущего значения или экспоненциальный спад, подогнанный по последним часам;
     - **до события: вероятность начала протонного события повышается после сильной вспышки** (класс, положение на диске, рост потока ≥10 МэВ). Вспышка — вход прогноза, а не отдельный риск. Цель — выиграть в заблаговременности у готового предупреждения SWPC, которое на событиях мая–июня 2024 давало 12–30 мин (§16);
     - неопределённость растёт с горизонтом;
  3. вероятности RSGA и 3-дневного прогноза — грубая оценка по суткам или 3-часовым интервалам;
  4. ничего нет → «нет данных».

**Геометрия G(t):** Rc вдоль трассы и флаг ЮАА. **Kp — только модификатор Rc**: расширяет открытую зону к экватору.

**Условие на траектории** (слой 2, §5.1): `high` / `elevated` / `nominal` / `no_data` по минутам. **Последствие** (слой 3): класс по таблице §5.3.

Ограничение, которое выводится явно: поток на геостационаре (GOES) — показатель обстановки, а не доза внутри скафандра. Шкалы S, G и R несопоставимы.

### 9.5. Механизм 2 — микрометеороиды и орбитальный мусор (MMOD)

**Сближения — стоп-фактор по принципу «да/нет»** (§5.3, §21 п. 2):

- Источник 1 — **SOCRATES**: готовые сближения на 7 суток с порогом минимальной дальности 5 км. Этого может не хватать: у МКС зона контроля вытянута вдоль орбиты. По открытым материалам NASA — порядка ±2 км по высоте и ±25 км вдоль и поперёк орбиты; значения нужно проверить и вынести в `thresholds.yaml`.
- Источник 2 — **собственный отбор** (рекомендация постановщика: взять объекты, которые находятся на орбите МКС):
  1. из каталога GP берутся объекты, чей перигей и апогей пересекают полосу высот МКС. По CelesTrak `GROUP=active` на 2026-09-18 таких 519 из 16 583. Мусор у CelesTrak есть только отдельными группами; полный каталог — в Space-Track;
  2. SGP4 векторно по сетке, поиск проходов через зону контроля и моментов наибольшего сближения;
  3. расчёт после каждого обновления каталога, а не на каждый запрос. Результаты лежат в `conjunctions` с пометкой источника.
- Сближение в окне (плюс запас на задержку) → `critical`, окно «не рекомендуется». Это не вероятность попадания в космонавта: она не оценивается, что сказано в объяснении.
- История (май–июнь 2024): собственный отбор по историческим элементам каталога из Space-Track `GP_HISTORY` с отсечкой по `CREATION_DATE`. Без доступа к нему — «нет данных» по сближениям, окно «требует проверки».

**Метеорные потоки** — второстепенный, класс не выше `undesirable`: коэффициент к фону из прогноза NASA MEO × (1 − экранирование Землёй по видимости радианта). Прогноз опубликован заранее (2023-11-02 для 2024 года) и пригоден для строгого replay.

### 9.6. Горизонт прогноза и уверенность

| Фактор | На сколько вперёд известен |
|---|---|
| Орбита | дни (OEM на 15 суток, плановые манёвры в нём) |
| Метеорные потоки | год |
| Сближения | до 7 суток, уточняются ближе к моменту |
| Геомагнитная буря | 1–3 суток, если CME уже произошёл; ошибка времени прихода порядка ±10 ч |
| Солнечные протоны | до вспышки — только вероятность на сутки; после вспышки — повышенная вероятность на часы; после начала события — длительность и спад |

- Период поиска до 24 ч — гарантированный режим. До 72 ч — разрешён, уверенность по космической погоде за пределами суток явно понижена.
- Уверенность каждого интервала: `high` (свежее наблюдение), `medium` (действующее предупреждение SWPC, свой прогноз в пределах 6 ч), `low` (вероятности на сутки), `none` (нет данных). У каждой оценки есть текстовое обоснование.
- **Когда пересчитать.** Время следующих выпусков берётся из `sources.yaml`. Пример: «прогноз на окно уточнится после выпуска SWPC в 12:30 UTC».

### 9.7. Окна и правило выбора

- Кандидаты — окна заданной длительности с шагом 10–15 мин по периоду поиска. Всегда включаются плановое окно и окна, которые явно задал пользователь.
- По каждому механизму: минуты по классам, минуты `no_data`, полнота, минимальная уверенность. Отдельно — **устойчивость к задержке** (§9.8).
- Ступенчатое правило:
  1. Есть `critical` в окне по любому механизму → «не рекомендуется». Окно показывается с причиной, но в выбор не входит.
  2. Нет данных по критическому фактору в окне → «требует проверки».
  3. Среди оставшихся: если окно не хуже другого по всем механизмам и лучше хотя бы по одному (минуты `undesirable`) → лучше.
  4. Если окна несравнимы (одно лучше по радиации, другое по метеорам) → применяется документированный приоритет механизмов (радиация выше метеоров), **а компромисс показывается явно**.
  5. При равенстве: лучше окно с большим запасом на задержку.
  6. Разница в пределах неопределённости → «равнозначно».
  7. Все окна «не рекомендуется» / «требует проверки» / низкая уверенность → «нет окна без критических факторов» или «недостаточно оснований для рекомендации».
- Изменение длительности — это **новый план**, который сравнивается только с окнами той же длительности.
- В результате фиксируется номер сработавшего правила и факторы и интервалы, которые на него повлияли.

### 9.8. Этапы ВКД и отклонение от графика («стрессовый сценарий»)

Постановщик: любое отступление от циклограммы выхода — уже стрессовый фактор; изменение внешних условий может привести к сокращению или отмене ВКД (§21 п. 4). В постановке это доп. функция «моделирование этапов ВКД».

| Параметр | Смысл | По умолчанию |
|---|---|---|
| `return_to_airlock_min` | сколько нужно экипажу, чтобы вернуться в шлюз из рабочей зоны | уточнить у экспертов |
| `overrun_margin_min` | запас на задержку работ | 60 мин (условно) |
| `phases` | опционально: выход из шлюза, переход, работы, возвращение | одна фаза «работы» |

Что считается:

- **Устойчивость к задержке:** через сколько минут после планового окончания начинается первый `critical`. Пример: «если выход затянется на 45 мин, он попадёт в открытую зону при повышенном потоке».
- **Запас на реакцию:** для каждого прогнозируемого критического события в окне — сколько времени между предупреждением и началом события в сравнении с `return_to_airlock_min`. Предупреждение, пришедшее позже этого времени, помечается как запоздалое.
- **Сценарии «условия изменились»:** при пересчёте идущего или утверждённого плана система предлагает: продолжать / сократить до момента X / перенести / вернуть экипаж. Выбор остаётся за человеком.

### 9.9. Объяснения и доказательства

- Объяснение собирается из фактов, а не пересказывает уровень угрозы. Пример: «B лучше A: в A 34 мин в открытой зоне при потоке S1 (наблюдение GOES, 02:55 UTC); в B — 0; по MMOD окна равнозначны; B устойчиво к задержке до 70 мин».
- Каждое доказательство: слой (измерение / условие / последствие), тип, значение и единицы, время, `issued_at`, источник, `raw_ref`. Через `GET /raw/{raw_id}` открывается исходный текст или строка файла.

### 9.10. Отслеживание и оповещения

- `watch` — утверждённый план: окно, параметры ВКД, каналы оповещения, срок действия.
- **Триггеры пересчёта:** `NOTIFY new_data` по источникам, от которых зависит план; смена статуса источника; таймер (раз в 5 мин, чтобы заметить устаревание).
- **Когда оповещать:**
  - класс в окне ухудшился (`acceptable → undesirable → critical`);
  - появилось сближение или протонное событие в окне;
  - пропали данные по критическому фактору;
  - вышел новый прогноз, меняющий уверенность.
- **Без спама:** одно оповещение на пару (план, эпизод), дальше только эскалации; подтверждение аналитиком; гистерезис на границах порогов.
- **Задержка** «данные опубликованы → оповещение доставлено» записывается в `alerts` и показывается. Цель — §14.
- Каналы: консоль (SSE), Telegram, строка статуса (§10).

### 9.11. Сверка прогноза из прошлого (verify)

- Выполняется отдельно от прогноза: подгружаются данные после T, прогноз не меняется.
- Показатели: состоялось ли событие, попало ли в окно, заблаговременность предупреждения **в сравнении со временем возвращения в шлюз**, ложные предупреждения, пропуски.
- Сравнение с базовыми подходами на тех же условиях: «последнее наблюдение» и «одно готовое предупреждение SWPC».

## 10. Сервис `report` — интерфейсы и каналы

Эксперты: нужен профессиональный и упрощённый вариант интерфейса; для экипажа — «супер маленькая строчка» (§21 п. 6).

### 10.1. Консоль аналитика (профессиональная)

Под рабочее место в ГОГУ: плотная информация, время по Москве (МСК; в API и выгрузках — UTC), несколько панелей на одном экране.

- запрос;
- результат: шкала по механизмам и слоям, трасса, предупреждения, таблица окон, регуляторы начала, длительности и запаса;
- боковая панель доказательств;
- панель источников: статусы, свежесть, «обновить», заморозить или отключить для расчёта;
- отслеживаемые планы и лента оповещений;
- вкладка сверки (replay);
- сохранённые расчёты.

### 10.2. Краткая сводка (упрощённая)

Для передачи рекомендации руководителю. Одна страница, пригодна для печати: светофор по окнам, рекомендованное окно, 3 ключевые причины, критические факторы, ограничения, «когда пересчитать».

### 10.3. Строка статуса (доп. функция)

Для экипажа или внешнего дисплея, не длиннее одной строки:

```
ВКД 06:00–12:30 · РАД ● прием. · MMOD ● прием. · данные 4 мин · пересчёт 12:30
```

### 10.4. Telegram

Оповещения по отслеживаемым планам, краткая сводка и ссылка на консоль. Основной пользовательский путь, по которому оценивают интерфейс, — веб-консоль.

### 10.5. Экспорт

`GET /runs/{id}/export.zip`:

- `report.html` — полный отчёт; `brief.html` — краткая сводка;
- `run.json` — машиночитаемый результат (§11);
- `series/*.csv` — временные ряды, использованные в расчёте;
- `manifest.json` — сырые файлы (sha256, url, `issued_at`), версии парсеров и алгоритма.

**Статусы в интерфейсе:** загрузка, ошибка, неполные данные, «реконструкция», «автономный режим», «данные устарели на N мин» — всегда видны рядом с результатом.

## 13. Сбои, неполные данные и автономный режим

- Различаем **«воздействие не выявлено»** и **«данных недостаточно»**. Второе никогда не отображается как благоприятная обстановка.
- Источник в статусе `stale` / `error` / `disabled`: уже полученные данные доступны с отметкой давности. Интервалы, которые должен покрывать этот источник, получают `no_data`, окно — «требует проверки». По отслеживаемым планам уходит оповещение о потере данных.
- HTTP-ошибка, квота, таймаут, сбой разбора → статус источника, сообщение пользователю, повторная попытка с растущим интервалом. Сервисы не падают.
- **Автономный режим** (§21 п. 7):
  - все сервисы, модели и библиотеки работают локально, облачных API в пути расчёта нет;
  - без внешней сети `ingest` переводит источники в `error`, а расчёт идёт по кешу с явной давностью. Интерфейс показывает плашку «автономный режим, данные на ЧЧ:ММ UTC»;
  - пакет для изолированной машины: образы контейнеров, дамп БД с загруженными архивами, конфиги;
  - обоснование: условия работы ГОГУ и станции, плюс нестабильная доступность части зарубежных источников из нашей сети (§15).

## 14. Производительность и эксплуатация

| Показатель | Цель |
|---|---|
| Отклик интерфейса на «Рассчитать» (задание создано, прогресс виден) | < 1 с |
| Расчёт для периода поиска 24 ч | ≤ 5–10 с |
| Расчёт для периода поиска 72 ч | ≤ 20 с |
| Задержка оповещения: публикация источником → доставка | ≤ интервал опроса + 1 мин (алерты SWPC: ≤ 6 мин) |
| Пересчёт отслеживаемого плана после новых данных | ≤ 30 с |

Как достигается: предрасчёт трека МКС на 72 ч и сближений после обновления эфемерид и каталога; векторный SGP4; ядро без сети и файлового ввода-вывода.

**Эксплуатация:**

- Сервис должен работать **как минимум до середины понедельника, 21.09.2026** (§21 п. 12). Разворачиваем на VPS заранее и обновляем по ходу, не на ноутбуке.
- `docker-compose` с `restart: unless-stopped`, проверки работоспособности у каждого сервиса, «пульс» планировщика в `source_status`.
- Ежедневная резервная копия БД. Логи ошибок источников доступны на панели источников.
- Доступ жюри: публичный адрес, инструкция в README.
