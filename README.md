# Прогнозирование внешних рисков и планирование ВКД на МКС

Исследовательский прототип поддержки решений для аналитика группы планирования выходов в открытый космос.
КосмоХакатон 2026. Архитектура — [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

Сервис сравнивает окна ВКД одинаковой длительности по двум механизмам внешнего воздействия:

1. **Радиационная обстановка на траектории** — солнечные протоны (GOES) с учётом геомагнитного обрезания
   в точке МКС (IGRF, Kp) и проходы Южно-Атлантической аномалии.
2. **Мусор и метеороиды (MMOD)** — сближения с отслеживаемыми объектами (собственный отбор по каталогу Space-Track на
   высотах МКС; проход через зону контроля — стоп-фактор: при относительной скорости до 15 км/с 1 г вещества несёт
   ~100 кДж) и метеорные потоки по годовому прогнозу NASA MEO (мелкие частицы статистически, с экранированием Землёй).

Режимы: «сейчас», «история: прогноз из прошлого» (replay) с отсечкой по времени публикации данных и сверкой с фактом,
«история: разбор» по полному архиву.

## Состав

| Сервис | Порт | Что делает |
|---|---|---|
| `report` | 8000 (наружу) | веб-консоль аналитика, краткая сводка, полный отчёт, ZIP-экспорт, доставка оповещений (SSE); проксирует остальные сервисы |
| `ingest` | 8001 (127.0.0.1) | сбор данных по расписанию, сырые файлы, статусы источников, выгрузка CSV |
| `assessment` | 8002 (127.0.0.1) | расчёт окон, объяснения, доказательства, сверка replay, отслеживание окон и оповещения |
| `db` | — | PostgreSQL |

## Консоль

`http://<сервер>:8000`. Разделы:

- **Расчёт** — два уровня: основной экран упрощённый (ответ, почему, полоса всех вариантов начала); кнопка
  «Подробности» — профессиональный вид: временная шкала по механизмам (клик по полосе — доказательства и исходные
  файлы), таблица окон с правилом выбора и изменением длительности, трасса МКС, данные расчёта, «Что было на самом деле»
  (сверка), сохранение (отчёт, сводка для руководителя, ZIP, JSON, строка статуса). Режим: «Сейчас» или «Прошлая дата»
  (прогноз из прошлого; с галочкой «Разбор» — по полному архиву); готовые примеры 2024 г.
- **Источники** — все источники, которые собирает ingest: что в них, откуда скачиваем, свежесть, следующий опрос,
  сколько сохранено; «Обновить» по каждому и «Обновить все», заморозка, выгрузка CSV, состояние архива.
- **Оповещения** — отслеживаемые выходы и сообщения об изменении обстановки, фильтры, «принято».
- **Сохранения** — все расчёты с кратким ответом: открыть заново, назвать, сводка, ZIP, удалить.

Время в консоли, отчётах и оповещениях — московское (МСК = UTC+3); в API, JSON и CSV — UTC.

## Оповещения

1. В консоли выберите вариант и нажмите «Следить и предупредить, если станет хуже» (режим «Сейчас») или «Показать
   предупреждения, как в тот день» (прошлая дата).
2. `assessment` пересчитывает окно тем же ядром: в реальном времени — по сигналу о новых данных от `ingest`
   (PostgreSQL LISTEN/NOTIFY) и раз в 2 мин; в проигрывании — «часы» идут шагом 30 мин каждые ~5 с,
   на каждом шаге видны только данные, опубликованные до текущего момента «часов».
3. Оповещение создаётся при изменении состояния окна: критический интервал (со временем до него и сравнением со
   временем возвращения в шлюз), ухудшение, пропажа данных, улучшение. Повторов по тому же состоянию нет.
4. Доставка: лента и всплывающие сообщения в консоли в реальном времени (SSE), системное уведомление браузера,
   Telegram — если в `.env` задан `TELEGRAM_BOT_TOKEN`. Получатель открывает бота и нажимает Start — бот отвечает
   «✅ Оповещения подключены» и запоминает чат. Команды — кнопками под полем ввода и в «Меню»: «📋 Что отслеживается»
   (/status), «🔔 Проверить связь» (/ping), «🔕 Отключить оповещения» (/stop), «❓ Помощь» (/help). В Telegram приходят
   и «Слежение включено» / «Слежение завершено», чтобы было видно, что бот работает.
5. В разделе «Оповещения» консоли — куда уходят сообщения (эта страница, браузер, Telegram: кто подключён, кнопка
   «Проверить связь»), подтверждение после «Следить…» и живой индикатор у каждого слежения (когда была проверка).
   Команды бота принимает один процесс на токен: если тот же токен запущен ещё где-то, в статусе будет «409 Conflict»
   (лишний экземпляр — остановить или `TELEGRAM_POLLING=0`).

Пример проигрывания 08.06.2024 (окно 06:00–12:30): в 05:00 по «часам» — «КРИТИЧНО с 07:33, уровень S3+», за 153 мин
(фактически S3 — в 08:00).

## Запуск в Docker

```bash
cp .env.example .env        # заполнить SPACETRACK_USER, SPACETRACK_PASSWORD, POSTGRES_PASSWORD
docker compose up -d --build
```

Проверка: откройте `http://<сервер>:8000` или `curl http://localhost:8000/health`
(отвечает `{"report":"ok","assessment":"ok","ingest":"ok"}`).

**Данные собираются сами при каждом старте `ingest`:**

- **Архив** (`archive.ranges` в [config/sources.yaml](config/sources.yaml)): проверочный период 27.04–02.07.2024 и
  отложенные для эксперимента события (08–24.02, 22–27.03, 08–13.10.2024). По каждому источнику ищутся дни без данных и
  загружаются. Пустая БД — всё (первый запуск ~15–20 мин), после перезапуска — только недостающее. Дни, которых нет у поставщика (пропуск 3-дневных прогнозов в архиве NCEI
  15.05–16.06), запоминаются и повторно запрашиваются не чаще раза в неделю; сбой сети — повтор при следующем старте.
  Ход загрузки — `GET /bootstrap` у `ingest` (в консоли — индикатор «архив: загружено N из M дней»), повторить —
  `POST /bootstrap`. Синхронно из командной строки: `docker compose --profile setup run --rm backfill`.
- **Живые данные:** первый опрос источника — по давности последней успешной загрузки (давно — сразу, свежие — по
  расписанию). Пропуск за время простоя догружается: протоны GOES — продуктом SWPC за 1/3/7 сут (старше — архив
  NCEI), Kp — из GFZ, сообщения SWPC — месячными архивами FTP, 3-дневный прогноз и RSGA — из архива NCEI, элементы
  МКС — историей Space-Track, каталог — историей за последнюю неделю. Глубина догрузки — не больше 90 сут.

Сервисы перезапускаются автоматически (`restart: unless-stopped`). Сырые файлы лежат в `./data/raw`,
БД — в томе `pgdata`.

## Локально без Docker (SQLite)

```bash
python -m venv .venv && .venv/Scripts/pip install -r requirements.txt   # Linux/macOS: .venv/bin/pip
uvicorn services.ingest.api:app --port 8001          # планировщик + догрузка архива и пропуска при старте
# вручную: python -m services.ingest.cli bootstrap   — недостающие дни архива
#          python -m services.ingest.cli live        — один проход по живым источникам (с догрузкой пропуска)
uvicorn services.assessment.api:app --port 8002      # + отслеживание окон
uvicorn services.report.app:app --port 8000          # консоль: http://localhost:8000
python -m pytest -q
```

Без `DATABASE_URL` используется `data/app.db` (SQLite).

## Примеры

Прогноз из прошлого на момент 08.06.2024 03:00 UTC, выход 6 ч 30 мин, плановое начало 06:00:

```bash
curl -X POST http://localhost:8002/runs -H "Content-Type: application/json" -d '{
  "mode": "replay", "as_of": "2024-06-08T03:00:00Z", "duration_min": 390,
  "planned_start": "2024-06-08T06:00:00Z",
  "eva": {"return_to_airlock_min": 30, "overrun_margin_min": 60}
}'
# -> {"run_id": "r_...", "status": "queued"}
curl "http://localhost:8002/runs/r_...?include=summary"     # статус, рекомендация, объяснение
curl "http://localhost:8002/runs/r_..."                     # полный результат: шкалы, окна, ряды, доказательства
curl -X POST "http://localhost:8002/runs/r_.../verify"      # сверка с тем, что было на самом деле
```

Текущая обстановка, окно 4 ч в ближайшие сутки, источник протонов отключён для проверки поведения:

```bash
curl -X POST http://localhost:8002/runs -H "Content-Type: application/json" -d '{
  "mode": "now", "duration_min": 240,
  "source_overrides": {"goes_protons": {"state": "disabled"}}
}'
```

Из командной строки:

```bash
python -m services.assessment.cli run --mode replay --as-of 2024-06-08T03:00 --duration 390 --verify
```

Управление источниками: `POST /sources/{name}/refresh` (принудительно обновить), `/pause`, `/resume`
(заморозить обновление; заморозка общая для всех пользователей и снимается сама через 2 ч — `ingest.pause_max_min`).
Проверить сбой только в своём расчёте — `source_overrides` в запросе (в консоли — «Дополнительно» → «Проверка сбоя»).
Выгрузка: `GET /export/records.csv?quantity=p_ge10&from=2024-06-08&to=2024-06-09`. Исходный файл записи:
`GET /raw/{raw_id}`; файлы Space-Track наружу отдаются только выдержкой по объекту
(`?locator=NORAD_CAT_ID:<номер>`, МКС — всегда): условия Space-Track ограничивают передачу данных третьим лицам.

## Эксперимент

```bash
python -m scripts.experiments --out examples/experiments   # ~3 мин; только часть: --cases sep_0608,hold_1009
python -m scripts.experiments_mmod                         # ~15 мин: устойчивость прогноза сближений
```

Прогноз из прошлого на протонных событиях и спокойных периодах, сверка с фактом; сравниваются собственный прогноз,
«последнее наблюдение» и «только предупреждения SWPC»; для сближений — насколько прогноз по элементам до момента T
подтверждается более свежими элементами в зависимости от заблаговременности. Случаи проверочного периода (май–июнь) использовались при отладке,
поэтому независимая проверка — отложенные события февраля, марта и октября 2024 г. Результаты и выводы —
[docs/experiments.md](docs/experiments.md), сохранённые расчёты — [examples/](examples/).

## Воспроизводимость

Каждый расчёт сохраняется целиком (`runs`): запрос, отсечка, версия алгоритма, пороги и хэши файлов настроек
(`result.config`), манифест использованных сырых файлов (`result.manifest`) и доказательства со ссылками `raw_id` +
локатор. Сырые файлы не перезаписываются. Примеры сохранённых расчётов — [examples/](examples/).

Среда также закреплена: `requirements.txt` содержит точные версии runtime-зависимостей, а полный разрешённый набор
(включая транзитивные зависимости и линтер) — `requirements.lock`. Локальная проверка качества: `pip install -r
requirements.lock && ruff check . && pytest`; линтер в том числе запрещает немотивированные широкие `except`.

## Ограничения

Поток протонов GOES — показатель обстановки на геостационаре, оценка J_iss — не доза. Жёсткость обрезания — приближение
Штёрмера с эмпирическим сдвигом по Kp. Сближения рассчитаны по TLE; вероятность попадания в космонавта не оценивается.
Метеорные потоки — статистический прогноз, а не отдельные частицы. Решение о выходе принимают уполномоченные специалисты.
